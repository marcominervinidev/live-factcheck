# 0011: Gateway authentication for REST and WebSocket

- Status: accepted (part of the phase 1 plan approved on 2026-09-26)
- Date: 2026-09-26

## Context

Brief 3 and 15.5: no login or user management, but the gateway must not be open in the LAN. A token from the configuration protects REST and the WebSocket handshake, and tokens never appear in URLs (URLs end up in Caddy and Fastify logs). Browsers cannot set custom headers on a WebSocket handshake, so the usual `Authorization` header does not work there. Cookies would work but need a login endpoint and CSRF protection, which is more than a single shared token justifies.

## Decision

- **Secret** `GATEWAY_TOKEN` (Compose secret `gateway_token`, generated by `make secrets-init`, at least 32 characters). Compared in constant time (`crypto.timingSafeEqual` on SHA-256 digests, so the length does not leak either).
- **REST** (`/api/*`): `Authorization: Bearer <token>`; missing or wrong → `401` with `ApiError { code: "unauthorized" }`. No other hint.
- **WebSocket** (`/ws/session`): the connection is accepted, then the first text message must be `{ type: "auth", schemaVersion: 1, token }` within `WS_AUTH_TIMEOUT_MS` (5 s). Before that, nothing else is processed and no data is sent. Wrong token, other first message or timeout → `error` message and close with code 4401/4408. After auth the gateway creates the session (`session.ready { sessionId }`).
- **Browser storage:** the user enters the token once on the settings page; the app keeps it in `localStorage`. Risk: any script on the origin can read it. Mitigation: strict CSP (`script-src 'self'`, no third-party scripts), no user-generated HTML is rendered (evidence snippets are text), and the token only protects a personal LAN app, not user data. Rotation is `make secrets-init`-style replacement plus `--force-recreate`.
- **Sessions** live in Redis (`session:v1:{id}`, TTL = `MAX_SESSION_MS`), so any gateway replica can accept `POST /api/claims/check` for a session held open by another one; events reach the right replica via the session Pub/Sub channel (brief 6.7).
- **Limits:** request body 4 KiB for `/api/claims/check`, WebSocket messages 64 KiB (audio frames in phase 2 re-evaluate this), rate limit on text-mode checks (`RATE_LIMIT_CHECKS_PER_MINUTE`, shared via Redis across replicas), maximum session duration.

## Alternatives

- **Token as query parameter on the WebSocket URL:** simplest, but lands in access logs (brief 15.5 forbids it).
- **`Sec-WebSocket-Protocol` header carrying the token:** works in browsers, but the value is logged by some proxies and misuses the header.
- **Cookie session with a login form:** proper for multi-user, overkill for one shared token (brief 3).

## Consequences

- A reconnect creates a new session: verdicts for claims submitted in the old session are not replayed. Acceptable for text mode (the user can resend); phase 2 may add `resumeSessionId` to the auth message with a contract bump.
- The token in `localStorage` is readable by same-origin scripts; the CSP is therefore a security control, not only hygiene, and must stay strict.
