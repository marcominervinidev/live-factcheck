Erkennung · D1 – diagnose logs for detection drops and research (2026-10-02, branch feat/d1-diagnose-logs)
=========================================================================================================

Plan .ai/plans/feature-erkennung-absatz.md (grilling round 3, decisions 17 and 18), task D1; #79
(drops were counted but never logged), #80 (the "claim checked" line names the reason, not where
the evidence got lost).

Trigger: in the owner's test run of 2026-10-02 eight segments ended as provider_error, and nothing
said whether Jev or Claude failed; later two claims ended no_evidence although a test search for
the Berlin rents returned 26 results.

What the logs now say (never segment text, claim text, queries, URLs or error messages):
- claim-extractor, one line per dropped final segment, msg "segment dropped":
    {"sessionId":…,"segmentId":…,"reason":"not_a_claim"}                                    (info)
    {"sessionId":…,"segmentId":…,"reason":"provider_error",
     "failure":{"source":"classifier","kind":"provider_error","status":429,"error":"RateLimitError"}}   (warn)
  The failure walks the cause chain, so status and SDK class survive the double wrapping of the
  llm classifier (ClassifierError → LlmError → SDK error). refused and invalid_llm_output carry a
  failure too and log at warn.
- fact-checker, one line per researched check, msg "research summary" (shape pinned by the unit
  test "shows where a check without evidence lost it"):
    {"sessionId":…,"claimId":…,"queries":1,"fallbackQueries":false,"longNumberQueries":0,
     "documents":{"wikipedia":0,"web":0},"factChecks":0,
     "failedSources":[{"source":"wikidata","error":"FetchFailedError","status":429}],
     "web":{"queries":2,"failedQueries":0,"results":8,"pages":5,"skipped":{"http_403":5}},
     "snippets":0,"verdict":"nicht_pruefbar","reason":"no_evidence","retrieveMs":10,"classifyMs":0}
  `relevant` and `sufficient` appear once those steps ran, so the line shows which of the three
  no_evidence exits fired: snippets 0 (nothing found), relevant 0 (nothing relevant), sufficient
  below 0.5 (not enough). Skip labels: timeout, robots, blocked, http_<status>, content_type,
  too_large, fetch_failed, unreadable, or an error class. A tier or page cut off by our own
  timeout counts as `timeout`, never as robots.txt or a failed fetch. A cached verdict and a
  budget stop do no research and log no summary; an error in the hook never changes the answer.

4. What the lines do not show yet (candidates for R1, not for D1)
   - Wikipedia page loads that fail are swallowed inside the Wikipedia tier, so
     documents.wikipedia 0 can mean "no hit" or "the pages failed".
   - Chunks beyond MAX_CHUNKS_PER_DOCUMENT (6) per page are never ranked; a relevant sentence deep
     in a long article does not reach the relevance question.
   - A failed SearXNG query counts in web.failedQueries; its HTTP status stays inside the
     SearchError message, which is never logged.
